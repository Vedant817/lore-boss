- **Atomic writes — high confidence.** `src/db/store.ts:457` places the delivered-event claim, optional viewer, damage/block, boss and optional finisher writes in one synchronous transaction. No outer transaction encloses the child commit/publication. A real SQLite damage-trigger abort left the parent chat and parent claim present, with child claim, viewer and damage absent and no combat messages.
- **Duplicates and no-ops — high confidence.** `src/runtime.ts:201-213` durably claims newly ignored events. A newly claimed no-op returns `true`, preserving the consumed cooldown; a durable duplicate returns `false`, restoring the prior cooldown. A cooldown rejection does not mutate that cooldown. Independent probes confirmed an expired-cooldown duplicate cannot suppress the next attack and a full-health heal still consumes the shared attack/heal cooldown. The supplied block regression also exercises a duplicate against a new strike.
- **Timers and spawn — high confidence from code inspection; timer fault cases independently unexecuted.** Strike start/land use the same transaction and exception boundary at `src/runtime.ts:281`. Strike scheduling is assigned after successful persistence; source stop clears scheduling and session authority. A retained strike after a failed landing cannot perform another DB write without a session. Spawn saves the fully started state before assigning it or scheduling/publishing at `src/runtime.ts:299-310`. Spawn remains a single-statement path and propagates its failure to the existing application error handler.

## Limits and nonblocking wording note

`ARCHITECTURE.md:89` correctly disclaims restart reconciliation, retry and resumable fights. Its phrase "nothing is broadcast" should be read narrowly as no uncommitted combat-success effects: existing `stopSource` at `src/runtime.ts:379` cancels an open prediction, which can later emit a cancellation/failure message, and the independent probes intentionally use replay with no open prediction. The smallest wording improvement is "no uncommitted combat-success effects are emitted." This is a documentation precision note, not an atomicity blocker.

The exceptional-write guarantee assumes the transaction rollback and existing source-stop cleanup can themselves complete. Persistent disk failure, failure of `endSession`/file close during cleanup, process termination, nested transactions introduced by future callers, or a post-commit broadcaster/recording exception were not fault-tested here. Post-commit exceptions cannot roll back rows or retract already emitted effects. Seen/cooldown bookkeeping is intentionally retained on thrown failures; no retry/recovery promise follows from a rolled-back claim. Existing source stopping does not dispose the Runtime's unrelated periodic timers. No live prediction, provider, recording-file, browser or crash-recovery behavior was verified.
