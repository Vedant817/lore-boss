## Five concrete merit and implementation risks

1. **Community benefit is still an unsupported leap.** High competitive importance; high confidence in missing evidence, uncertain actual audience outcome. `DEVPOST_SUBMISSION.md:63`, `README.md:115`, and captions for 00:20.860–00:52.860 explicitly identify solo rehearsal; 01:10.060–01:37.060 substitutes labeled fixture participants for the cooperative example. This does not demonstrate that strangers understand blocking, enjoy healing the enemy, or return for another boss. Counterevidence: real chat, actual result persistence and synthetic distinct-user mechanics establish more than a slide concept. Smallest repair: a consented small-group playtest, recording unaided command comprehension, moderator effort and desire for another round. Report actual observations; do not manufacture traction. Not a formal eligibility blocker.

2. **The lore risks being a cosmetic layer on a generic fight.** High competitive importance; medium-high confidence, subjective novelty assessment grounded in source. `src/boss/reducer.ts:45` copies approved text into the name/attack pool; damage and strike rules at `:49–87` do not depend on lore meaning. `src/runtime.ts:314,317–318` rotates attack text and templates recap lines. Counterevidence: personal meaning can itself create entertainment, and moderator approval prevents publicizing arbitrary model output. Smallest repair: first demonstrate one real community recognizing and reacting to its own lore; if that fails, prototype one moderator-controlled story-specific interaction. Extra AI prose alone would not resolve this concern. No product change was made in this review.

3. **Setup asks too much of an unproven entertainment payoff.** Medium-high adoption risk; high confidence in required steps, unmeasured abandonment. `README.md:58–75` requires Node/native SQLite compatibility, local token handling, app registration/client secret, broadcaster authorization, inference configuration and OBS setup. The fixture bypasses those steps for judges (`:28–50`), not for actual streamers. Counterevidence: the instructions are concrete, the fixture is isolated, and viewers themselves only need ordinary chat. Smallest repair: observe one new streamer following the existing runbook and fix the first measured blocker; publish measured setup time only after that exercise. This is an ease-of-use deduction under §6 Design, not a demand for hosted deployment.

4. **Stun damage notation can imply the multiplier is applied twice.** Low-to-medium presentation severity; high confidence in displayed/source behavior, medium confidence in viewer confusion. Supplied encoded still `03-live-stun.png`, within 00:20.860–00:52.860, shows HP 5/25, a floating `−20 ×2`, and a separate `−20` popup for the hit. `src/boss/reducer.ts:83` already doubles the amount; `src/runtime.ts:199–205` sends that actual HP difference; `src/overlay/overlay.js:254,267` prints both the difference and an additional multiplication marker. This is not a demonstrated scoring error: the actual hit is 20. Counterevidence: the yellow stun badge explicitly says double damage and the HP change is correct. Smallest repair: show `20 damage · stunned bonus` or one explicit `10 × 2 = 20` presentation, with one primary numeric effect. Confirm comprehension at normal stream size. No full-motion duration or overlap claim is inferred from this still.

5. **Invalid candidate rejection has weak operator diagnostics.** Medium operability severity; high confidence in static control flow, not reproduced through a live provider. `src/lore/service.ts:14,19–23` returns the same empty array for invalid schema/evidence/blocked output as for a legitimate empty candidate list; `:45–46` then clears `error`. `tests/lore.test.ts:9–11` confirms intentional rejection but does not turn it into a distinct operator outcome. Thus valid JSON with unusable candidate content can look like successful extraction with nothing found. Separately, `DEMO_SCRIPT.md:9` records an initial readiness HTTP400; its cause remains UNVERIFIED and I do not attribute it to this validation path. Counterevidence: unsafe candidates never become lore, malformed transport/assistant JSON does throw, timeouts are bounded (`src/llm/client.ts:30–43`), and later extraction succeeded. Smallest repair: distinguish safe rejection from legitimate no-results with a non-sensitive reason/status; preserve fail-closed behavior and avoid echoing provider bodies or chat. No automatic retry/fallback is proposed.
